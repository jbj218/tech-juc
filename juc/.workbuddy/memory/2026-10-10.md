## JUC 项目（D:/ideaProject/juc）学习问答

### 一、pc 包：if vs while 虚假唤醒（A.java / B.java / C.java）
- 现有三份代码全用 `while`，且 `A.java` 是 4 线程（A/C 为 increment、B/D 为 decrement）+ `notifyAll`，属「必现出错」配置。
- 解释链路最终落到**字节码层面**：`while` 编译后在 `wait()` 之后有一条 `goto` 跳回条件判断；`if` 没有，于是唤醒后直冲业务代码。
- 纠正的关键误解：「C 线程唤醒后从上到下执行」——错。`wait()` 是**挂起点**不是方法结束，唤醒后从 `wait()` 的**下一行**继续，不会重走 `if`。所谓「跳过」实际是 `if` 在挂起前已执行完。
- 「偶发」一词的适用范围：仅对 2 线程 + OS spurious wakeup 成立；多线程 + `notifyAll` 场景下出错是**必然**，只是「哪一轮错」偶发。虚假唤醒是 POSIX 规范明确允许的行为。
- 边界结论：`number` 越界变负后会导致生产者永久挂起（假死），所以 `while` 是硬性规范而非可选项。
- 顺带指出 `B.java` 第 86 行 `decrement()` 误带 `synchronized`（内部用 `lock.lock()`，多余且语义混乱）。

### 二、Lambda 捕获局部变量（CyclicBarrierDemo.java）
用户连续 5 轮追问，核心误解是**把「变量生命周期」和「值生命周期」混为一谈**，且多次认为「final 也属于 main 线程、也会随 main 消失」。

讲透的几个关键点（后续复用此口径）：
1. **捕获的永远是值副本**，不是变量本身。编译期生成 Lambda 类，把值存成其字段（如 `arg$1`），可用 `javap -c -p` 验证。
2. **复制发生在的是 main 创建 Lambda 对象那一刻**，不是子线程执行时。`new Thread(() -> {...})` 里的 Lambda 对象由 main `new` 出来并传入 `temp` 的值 → 此后与 main 栈帧彻底脱钩。用户反复卡在「子线程运行时去够 main 变量」这个错误时序上，这是讲解的关键锚点。
3. **职责分离**：「复制到堆」解决**生命周期**问题；`final`/有效 final 解决**语义歧义**（避免副本与原值分家）。二者不可互换。
4. 循环变量 `i` 被 `i++` 重新赋值 → 不满足有效 final → **编译期报错**；`final int temp = i;` 必须在**循环体内**声明才能让每轮拿到独立副本（位置 + 不可变两个条件缺一不可）。
5. 对照验证：`cyclicBarrier`（第 12 行）未写 `final` 也能捕获，因为满足有效 final。
6. 字段不受此限制：字段住堆上，Lambda 持 `this` 引用访问，无复制需求。
7. **表述修正（用户指出「你在强行解释」后必须遵守的准确口径）**：
   - 不要说「编译器不能让它访问，所以偷偷抄」——这会让人以为先有一次访问动作被替换。准确说法：**编译后根本不存在「Lambda 访问外部变量」这个动作**，Lambda 被编译成一个独立的类，捕获值经**构造器**成为该类的成员变量。
   - **内含发生的时刻 = `new` 那一刻**。等价形式：`new Thread(new LambdaClass(temp)).start()`，与手写 `new MyTask(temp)` 完全一致。用户对「类里成员变量能内含」没有疑问 → 直接把该心智模型套到 Lambda 上即可，这是最有效的讲解路径。
   - 源码里看不到 `new LambdaClass(temp)` 的原因：被 `invokedynamic` 指令 + `LambdaMetafactory` 引导方法隐藏，运行时代劳实例化与传参。**有明确载体，不是魔法**。
   - 核心约束锚点：局部变量只能被**声明它的方法**访问，跨方法无语法。所以想让 `run()` 用上 `temp`，唯一解就是「提升为成员变量 + 构造器传入」。手写类与 Lambda 面临同一约束、同一解法，区别只在于手写类的 `new` 可见、Lambda 的 `new` 被隐藏。
