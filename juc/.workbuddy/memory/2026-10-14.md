## 用 AQS 实现自定义锁：需要掌握的方法清单

用户在 `lock` 包已有 `SpinlockDemo`（CAS 自旋锁，`AtomicReference<Thread>`），现在想进阶到 AQS 自研锁。

**分层结论**（这是讲这题的正确骨架）：
- **要覆写的钩子（protected，默认抛 `UnsupportedOperationException`）**：`tryAcquire(int)`、`tryRelease(int)`（独占）；`tryAcquireShared(int)`、`tryReleaseShared(int)`（共享）；`isHeldExclusively()`（仅用 Condition 时才需要）。
- **AQS 已实现的模板方法（public final，直接调用）**：`acquire`/`acquireInterruptibly`/`tryAcquireNanos`、`release`、`acquireShared`/`releaseShared`/`acquireSharedInterruptibly`/`tryAcquireSharedNanos`。排队、park、唤醒、中断、超时全在这里面，用户一行不用写。
- **操作工具**：`getState()`/`setState(int)`/`compareAndSetState(int,int)`；`getExclusiveOwnerThread()`/`setExclusiveOwnerThread()`（来自 `AbstractOwnableSynchronizer`）；`hasQueuedPredecessors()`（公平锁唯一要多写的一行）；`newCondition()`。
- **底层（不用碰）**：CLH 变体队列、`Node` 状态位（CANCELLED/SIGNAL/CONDITION/PROPAGATE）、`LockSupport.park/unpark`。

**关键认知**：AQS 只问一个问题 —— **`state` 是什么含义**。用户负责定义语义，AQS 负责排队与阻塞。
现成参照：`ReentrantLock` state=重入次数；`Semaphore` state=剩余许可；`CountDownLatch` state=剩余计数；`ReentrantReadWriteLock` 高 16 位读、低 16 位写。

**共享模式返回值语义**：负数=失败；0=成功但不再向后传播；正数=成功且需继续唤醒后继。

**tryRelease 的写法要点**：`setExclusiveOwnerThread(null)` 必须在 `setState(c)` **之前**（先清 owner 再写 volatile state，保证别人拿到锁时 owner 已经是 null）。

**分步落地顺序（给用户推荐的路径）**：非公平非重入（约 20 行）→ 在 `tryAcquire` 里判断 `getExclusiveOwnerThread() == current` 加重入 → 加 `hasQueuedPredecessors()` 做公平 → 加 `newCondition()` 支持 await/signal。

**定位区分**（用户已在 hmdp 写过基于 Redis 的分布式锁，别混）：AQS 解决的是**单 JVM 内**的线程排队；Redis 锁解决**跨进程**互斥。两者层次不同，不可互替。

### `isHeldExclusively() { return getState() == 1; }` 错在哪（用户拿这段代码来问）

**语义**（AQS Javadoc 原文）："reports whether synchronization is **exclusively held with respect to the current thread**" —— 问的是"**当前线程**是不是独占持有者"，不是"锁有没有被占用"。

**正确实现**（AQS Javadoc 的 Mutex 示例，源码 230-233 行原文）：
```java
public boolean isHeldExclusively() {
    // a data race, but safe due to out-of-thin-air guarantees
    return getExclusiveOwnerThread() == Thread.currentThread();
}
```
同示例里另有 `isLocked() { return getState() != 0; }`（源码 226-228 行）——**`getState()==1` 就是把 `isLocked()` 的语义错塞进了 `isHeldExclusively()` 的位置。**

**真值表（4 格只对 2 格）**：

| 实际状态 | `getState()==1` | 正确答案 | |
|---|---|---|---|
| state=0，无人持有 | false | false | 碰巧对 |
| state=1，自己持有 | true | true | 对 |
| state=1，**别人**持有 | **true** | false | ❌ 冒充持有者 |
| state=2，自己重入 | **false** | true | ❌ 不认自己 |

**AQS 内部的 6 个调用点**（JDK 19 源码 `AbstractQueuedSynchronizer.java`，行号已核对）：`ConditionObject.signal()` 1472、`signalAll()` 1487、`enableWait()` 1502（`await`/`awaitNanos`/`awaitUntil` 全走这里）、`hasWaiters()` 1793、`getWaitQueueLength()` 1812、`getWaitingThreads()` 1831；另 Javadoc 的 `tryRelease` 示例 218 行也调用它。全是 `if (!isHeldExclusively()) throw new IllegalMonitorStateException();`。

**实测对照**（脚本：`C:\Users\沨烨\AppData\Local\Temp\isheld\IsHeldTest.java`，可复用）：
```
测试1（重入 state=2 后 await）：
  getState()==1        → isHeldExclusively()=false → await() 抛 IllegalMonitorStateException
  owner==currentThread → isHeldExclusively()=true  → await() 正常返回，state 恢复为 2
测试2（未持锁线程调 signal）：
  getState()==1        → 静默通过（本应抛异常）

```

**顺带暴露的两个实现要点（写可重入锁必踩）**：
1. `tryAcquire` 里重入分支必须 `setState(c + arg)`，且空闲分支必须 `compareAndSetState(0, arg)`（**不能写 `(0,1)`**）。因为 `condition.await()` 返回时是靠 `acquire(savedState)` 恢复重入层数的，写死 1 会导致回来后层数丢失，随后的 `unlock()` 抛 IllegalMonitorStateException。
2. `tryRelease` 必须 `getState() - arg`（**不能写死减 1**），因为 AQS `enableWait` 是拿 `savedState` 调 `release(savedState)`。

**源码位置**：`D:\IJ\java\jdk-19.0.1\lib\src.zip` → `java.base/java/util/concurrent/locks/AbstractQueuedSynchronizer.java`（已解压到 `C:\Users\沨烨\AppData\Local\Temp\jdksrc`）。**AQS 官方 Javadoc 里的 Mutex 示例（源码约 200-270 行）就是最好的写法参照，比网上教程可靠。**

### 追问：「那我直接 return true 表示线程独占资源不就行了？」

`isHeldExclusively()` 返回 `boolean`，`return 1` 编译不过；按 `return true;`（恒真）理解。**结论：比 `getState()==1` 更糟 —— 等于把门卫整个撤掉。**

**实测三写法 × 两场景**（脚本 `C:\Users\沨烨\AppData\Local\Temp\returntrue\ReturnTrueTest.java`，结构照抄 AQS Javadoc 的 Mutex，`tryRelease` 里用 `isHeldExclusively()` 当门卫）：

| 写法 | 场景1 未持锁者 `signal()` | 场景2 未持锁者 `unlock()` |
|---|---|---|
| `owner==currentThread`（正确） | 抛 IllegalMonitorStateException，等待者不受影响 | 抛异常，锁仍归 main（state=1, owner=main） |
| `getState()==1` | 抛异常（此时锁空闲 state=0） | **解锁成功** → state=0, owner=null |
| `return true` | **放行（不抛）** | **解锁成功** → state=0, owner=null |

**场景2 是最致命的**：因为 AQS Javadoc 的 Mutex 示例就是把 `isHeldExclusively()` 当作 `tryRelease` 的门卫（`if (!isHeldExclusively()) throw new IllegalMonitorStateException();`）。门卫恒真 ⇒ **任何线程调 `unlock()` 都能成功，别人可以把你的锁打开**，而你还以为自己持有。

**场景1 实测是永久挂起，不是延迟**：闯入者的 `signal()` 被放行后，`doSignal` 会把节点从条件队列摘走（源码 1451 行 `if ((firstWaiter = next) == null) lastWaiter = null;`，1453-1454 行清 COND 位并 `enqueue(first)`）。等待者 7.4 秒后仍 `WAITING`，锁一直空闲（state=0, owner=null）；中途补一次合法的 `signal()+unlock()` 也救不回来 —— 因为 `firstWaiter` 已经是 null，后续任何 `signal()` 都找不到那个节点了。**即"通知丢失 + 永久挂起"。**

**本质**：`isHeldExclusively()` 不是"你要做的判断"，而是"你向 AQS 声明的事实"。AQS 拿它当权限门卫（`ConditionObject` 里 6 处调用：`signal` 1472、`signalAll` 1487、`enableWait` 1502、`hasWaiters` 1793、`getWaitQueueLength` 1812、`getWaitingThreads` 1831）。恒真 = 撒谎。而且这个钩子必须可被不同同步器复用 —— `Semaphore` 那类非独占同步器上根本不该返回 true。

**正确写法永远是**：`return getExclusiveOwnerThread() == Thread.currentThread();`

### 追问：「tryRelease 不是管放锁的吗？isHeldExclusively() 不是只标记吗？」

用户把"谁在问"和"谁在答"混了。关键澄清：

**`isHeldExclusively()` 只回答，不改任何状态。** 但它被问了 7 次，且问的人有三类，不是同一个：

| 谁在问 | 位置 | 用途 |
|---|---|---|
| AQS 自己（`ConditionObject` 内部） | 6 处：`signal` 1472 / `signalAll` 1487 / `enableWait` 1502 / `hasWaiters` 1793 / `getWaitQueueLength` 1812 / `getWaitingThreads` 1831 | 条件操作的权限门卫 |
| **你自己**（写 `tryRelease` 时） | AQS Javadoc 的 Mutex 示例，`tryRelease` 第一行 | 放锁前的合法性检查 |
| 外部业务代码 | `ReentrantLock.isHeldByCurrentThread()`（ReentrantLock.java 第 615 行 `return sync.isHeldExclusively();`） | 业务里问"我拿着锁吗" |

**`tryRelease` 里那句 `if (!isHeldExclusively()) throw ...` 不是 AQS 加的，是 Javadoc 示例作者加的**；`release(int)` 本身不会替你做这个检查。

**JDK 生产代码用的是另一种写法**（已核对 `ReentrantLock.java` 第 171-181 行）：
```java
protected final boolean tryRelease(int releases) {
    int c = getState() - releases;
    if (getExclusiveOwnerThread() != Thread.currentThread())   // ← 直接比 owner，不调 isHeldExclusively()
        throw new IllegalMonitorStateException();
    ...
}
```
`ReentrantLock.Sync` 的 `tryRelease` **没有**调用 `isHeldExclusively()`。两种写法等价，但直接比 owner 更好：不依赖钩子的实现是否正确（上一轮 `return true` 导致别人能开锁，根因就是检查绕了这一层）。

**一句话**：`isHeldExclusively()` 是事实提供者，`tryRelease` 是状态执行者；执行者干活前要先确认事实，于是"问"的动作写在 `tryRelease` 里，而"答"的动作写在 `isHeldExclusively()` 里。它不干活 ≠ 它没被用。

### 审查用户的 `com.kuang.aqs.SimpleLock`（他自称"太多疑惑"）

**两个"为什么"的源码依据**（JDK 19，已核对行号）：
```java
// 936-939 行
public final void acquire(int arg) {
    if (!tryAcquire(arg))
        acquire(null, arg, false, false, false, 0L);   // 排队 + park + 唤醒后重试 + 中断处理
}
// 1006-1012 行
public final boolean release(int arg) {
    if (tryRelease(arg)) {
        signalNext(head);          // ← 释放成功后唤醒同步队列后继，这行用户自己写不了
        return true;
    }
    return false;
}
```
→ `acquire`/`release` 的**第一件事就是调你的 `tryXxx`**；它们是模板（final），`tryXxx` 是插槽。**tryXxx 答"可不可以"，acquire/release 管"不可以之后怎么办"。** 直接调 `tryXxx` 就退化成自旋锁了。

**`tryRelease` 为什么不用 CAS**：① 独占锁同一时刻只有持有者能走到这里（这是 `tryAcquire` 的 CAS 已经保证的互斥），**没有竞争者**；② 更实际的是**没有失败分支可走** —— tryRelease 的返回值语义是"是否释放干净"（true → AQS 去 `signalNext`），没有"重试"这一路，必然成功的写入套 CAS 是多余。安全性靠 `volatile` 写 + 单写者。对比：`tryAcquire` **必须** CAS，那才是真竞争。
**顺序要点**：必须 `setExclusiveOwnerThread(null)` 在前、`setState(c)` 在后 —— `setState` 是 volatile 写，作释放屏障，保证 owner=null 对随后读到 `state==0` 的线程可见。反过来会有"state 已 0 但 owner 还是旧线程"的窗口。`ReentrantLock.Sync.tryRelease` 同样用 `setState`。
