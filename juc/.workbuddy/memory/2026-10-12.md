### 线程池参数：CPU 密集型 vs IO 密集型
- 判断依据：任务是否在等外部资源。纯计算 → CPU 密集；有 DB/RPC/文件/网络 → IO 密集；混合 → 拆两池。
- 参数：CPU 密集 = 核数 + 1；IO 密集 = 2 × 核数（起点值）。公式 `N = 核数 × 目标利用率 × (1 + W/C)`。
- 实测 W/C：`ThreadMXBean.getCurrentThreadCpuTime()` 与 `System.nanoTime()` 分别取 CPU/挂钟时间，`wc = (wallNs - cpuNs) / cpuNs`。
- 关键补充：线程池上限必须与下游容量对齐（DB 连接池 20 个，线程池开 200 无意义）；禁用 `Executors.newFixedThreadPool`（无界队列 OOM）。
- 面试版口径已给用户，用户确认采用。

### CompletableFuture（future/Demo01.java）
- 两个 1024 来自两处打印：`whenComplete` 回调里的 `t=>1024`，和最外层 `println(...get())` 的结果。
- `whenComplete` 是旁路观察，不消费结果，返回新 CF 透传原值。

### CAS 与 Integer 缓存（cas/CASDemo.java）
用户混淆「Integer 缓存池」与「CAS 比较语义」。两处必须分清：
- **`AtomicInteger` 内部是 `private volatile int value`（基本类型）**，`compareAndSet` 走 `Unsafe.compareAndSwapInt` 按数值比较 → **完全不受 -128~127 缓存影响**。2020 是安全的。
- **`AtomicStampedReference<V>` / `AtomicReference<V>` 存的是引用**，内部 `Pair<T>.reference`，CAS 用 `==` 比引用 → 泛型为包装类时才有坑。
- demo 之所以「看起来正常」，是因为 1/2/6 恰在缓存区间，`Integer.valueOf` 返回同一缓存对象。
- 实测验证（已跑通）：`new AtomicStampedReference<>(200, 1)` 后 `compareAndSet(200, 300, 1, 2)` → **false**（两个 200 是不同对象）；换成 1 → **true**。
- 用户 b 线程 CAS 失败（输出 `b2 CAS: false`, `b2=>3`）原因是 **stamp 不匹配**（拿到 1，实际已 3），与 Integer 缓存无关 —— 这是版本号防 ABA 生效。
- 实际运行输出（T2）：`b1=>1 / a1=>1 / a2=>2 / a3 CAS: true / a3=>3 / b2 CAS: false / b2=>3`。
